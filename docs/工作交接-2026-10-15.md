## 1. 路径与工作区（最重要，先读这段）

### 为什么有两条路径

| 路径 | 性质 | 能否构建 |
|---|---|---|
| `E:\2026\MagicMotion` | 纯 ASCII 副本 | ✅ **可以**（用它） |
| `E:\2026\魔法手势游戏` | 原始目录，含中文 | ❌ **不行**，AGP 直接拒绝 |

**根因**：Android Gradle Plugin 明确拒绝非 ASCII 路径：

```text
Your project path contains non-ASCII characters.
This will most likely cause the build to fail on Windows.
```

Unity 虽然可以用 ASCII 的 junction（如 `E:\mmproj`）启动，但子进程的 aapt2 / AGP 会解析出
真实中文路径，于是先后炸成三种完全不同的形态（见第 3 节），极具迷惑性。

### 如果还有代码留在中文目录

只在中文目录改了代码时，构建前同步一次（约 8 MB，几秒）：

```powershell
robocopy <中文目录>\Assets          E:\2026\MagicMotion\Assets          /E /MT:8
robocopy <中文目录>\Packages        E:\2026\MagicMotion\Packages        /E /MT:8
robocopy <中文目录>\ProjectSettings E:\2026\MagicMotion\ProjectSettings /E /MT:8
```

**不要同步 `Library`**（12 GB，且路径一变缓存就失效）。
**必须存在 `LocalPackages`**（MediaPipe tarball 249 MB），否则包解析失败。

## 3. 打包踩过的坑（**不要再踩一遍**，共失败 10 次才定位）

失败现象固定为 `:unityLibrary:generateDebugRFile` 抛 `java.lang.StackOverflowError`，
但**栈溢出只是表象**。以下 6 个方向全部**已被排除**：

| 误判方向 | 排除依据 |
|---|---|
| 系统内存不足 | 内存释放到 8.39 GB 后仍失败 |
| JVM 栈不足（`-Xss`） | `-Xss8m` / `-Xss16m` 均无效 |
| Gradle 堆（`-Xmx`） | 4096 → 2048 后仍失败 |
| Gradle 增量缓存损坏 | 清理 `build/`、`.gradle/` 后仍失败 |
| junction 路径不一致 | 两个 junction 都试过，均失败 |
| 项目代码改动 | 与 C# 无关，失败在 Gradle 阶段 |

**真正的两个根因**：

1. **中文路径**（主因）—— 见第 1 节
2. **`android-35\android.jar` 损坏**（次因）
   ```text
   aapt2.exe E LoadedArsc.cpp:94] RES_TABLE_TYPE_TYPE entry offsets overlap actual entry data.
   aapt2.exe E ApkAssets.cpp:149] Failed to load resources table in APK '...\SDK\platforms\android-35\android.jar'
   ```
   已绕过：`ProjectSettings.asset` 里 `AndroidTargetSdkVersion: 0`（自动→35）改为 **`34`**。
   （API 33/34/35 三个平台都装着，34 的 jar 是好的。）

### 附带的环境改动（都可逆）

| 项 | 原值 | 现值 | 说明 |
|---|---|---|---|
| `ProjectSettings.asset` 的 `AndroidTargetSdkVersion` | 0 | **34** | 绕开损坏的 android-35 |

| `Assets/Plugins/Android/gradleTemplate.properties` | 无 | 新增 | 见下 |

## 4. 代码改动清单

### 本轮（位置偏差兼容，用户提出的需求）

**`Assets/MagicMotion/Scripts/Motion/PushMotionTracker.cs`**

需求：手放在画面上下左右任意位置，推掌都要能识别。

原实现把掌心在画面里的**位移总量**当作「侧移」来拒绝，但推掌靠近镜头时，
**透视投影本身会让手在画面上向外移动**，手越靠边移得越多：

```text
手在画面中心推掌 → lateralDelta ≈ 0.05  轻松通过
手在画面边缘推掌 → lateralDelta ≈ 0.70  逼近阈值 0.80（maximumLateralDrift）
```

即**同样的推掌动作，手往边上挪一点就放不出技能**。

修法：不能简单减去「偏移 × 增长」——手**朝镜头**推时 `u=f·X/Z` 里 X、Z 同比例缩小，
画面位置几乎不动；手**平行光轴**推才会径向外移。真实动作介于两者之间，减任何固定量都会
在某些位置反向放大误差。

正确做法：**只放行径向「向外」的分量**，径向向内和切向仍算漂移：

```csharp
var radial = radialOffset.normalized;
var outward = Vector2.Dot(travelled, radial);
var tangential = travelled.x * radial.y - travelled.y * radial.x;
var inward = Mathf.Max(0f, -outward);
lateralDelta = Mathf.Sqrt(tangential * tangential + inward * inward) / initialWidth;
```

> ⚠️ 中途踩过的坑：第一版只算切向分量（径向全放行），导致 `Add_RejectsSidewaysMovement`
> 用例（手在左上 `(0,0)` 向右移动）的 `lateralDelta` 从 1.0 掉到 0.707，跌破阈值 0.75 ——
> 等于放开了一种误触。上面这版把「径向向内」也计入，该用例回到 1.0，仍正确拒绝。

### 防误触修复（第 5 轮真机测试后追加，已构建装机、待验证）

**`Assets/MagicMotion/Scripts/Motion/PushMotionTracker.cs`**

1. **去掉 `growth || depth` 放行** —— 改为 `growth` 唯一主判据，`depth` 只给置信度打半折加成。
   实测 landmark 深度噪声极大（正例也常为负），让它单独开门是误触发主因。
2. **透视漂移改为减预测值** —— 不再整段放行径向外分量：
   ```csharp
   var expectedDrift = radialOffset * (bestGrowth * config.assumedAxialShare);   // 0.5
   lateralDelta = (travelled - expectedDrift).magnitude / initialWidth;
   ```
   依据：纯轴向推掌画面外移 = `offset × growth`，正对镜头推 = 0，取中点假设后残余最小。
   （上一版"整段放行径向外"让横向挥手也算推掌。）
3. **收回重置** —— 一次检测后手掌必须回缩 `minimumRetractRatio=3%` 才允许下一次，
   修掉单次推掌反复 CAST（2.4 倍 → 1.0 倍）。
4. 新增 `pushmetrics` 诊断日志：`growth= depth= vel= lateral=`，真机调阈值看它。
