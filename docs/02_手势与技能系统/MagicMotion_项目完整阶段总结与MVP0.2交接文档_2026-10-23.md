## 0. 新对话快速恢复摘要（优先阅读）

**产品**：Magic Motion，Unity + MediaPipe 的 Android 第一人称手势魔法体感游戏，现阶段优先开发**魔法练习室**验证可行性，再开发正式关卡战斗。

**现有代码基线**：`E:\2026\MagicMotion`，`main`，tag `v0.1.0`，基线提交 `67b4d7c`。已经实现摄像头 → 手部追踪 → `OpenPalm + Forward + Push` → `SK001 震山掌` → 魔法弹体击中石魔。此链路需要保留，并避免随意修改已冻结识别阈值。

**下一版本方向**：**Magic Motion MVP 0.2：魔法练习室（剑指系）**。先做分步骤教学、自由施法练习、固定训练目标、识别统计和四系符文；掌系和拳系预留入口与可扩展架构，不在当前版本做完整技能。

**已确认核心施法流程**：
1. 玩家结剑指，**手背朝向屏幕/手机摄像头**；
2. 保持剑指，翻转至**手心朝向屏幕/手机摄像头**；
3. 生成在**剑指指尖前方**、跟随手指移动的**基础纸符**；
4. 保持剑指，手向**上→雷、下→火、左→水、右→风**移动，选定元素；
5. 元素符成型并锁定，在指尖前持续跟手待命；
6. 切换张掌并向前 **Push**，符文转移至掌前并释放相应攻击。

**视觉和显示**：中式玄幻/道术纸符，实体黄色符纸、朱砂/能量符纹及四元素能量；**横屏 16:9 为主（设计基准 1920×1080）**，未来手机投屏电视；第一人称只显示当前施法虚拟手，背景为训练场和石魔，HUD 尽量简洁。允许底层追踪双手，但当前仅一只手是活动施法手，施法中不自动切换。

**目前尚未实现/未验证**：剑指和有序翻掌、新符文状态机、四方向选符、指尖跟随、四元素攻击、练习室 UI、虚拟手骨架驱动都属于后续开发事项；不能当作现有 v0.1.0 成果。跨设备/左手/双手/独立回归样本/15 分钟运行验证尚不完整。

**推荐下一步**：实现并验收 `MediaPipe → 虚拟施法手骨架映射 → 剑指与手背/手心 → 翻掌序列` 的独立验证模块，然后逐步接入召符、方向选符、待命、Push 技能路由和练习室界面。先做 debug/训练功能，再接正式特效。

## 2. 产品路线与魔法体系

### 2.1 新阶段定义【已确认需求】

`MVP 0.1 手部识别与震山掌闭环` → **`MVP 0.2 魔法练习室（剑指系）`** → `正式游戏（关卡/怪物/成长/多魔法体系）`。

练习室兼具三重任务：
1. **教学**：逐步学会标准起手、翻掌、选符、待命、释放。
2. **练习**：自由重复施法并看到真实游戏技能效果。
3. **可行性验证**：记录动作成功率、误触发、重复触发、耗时、帧率和识别问题，为进一步开发提供证据。

### 2.2 魔法分类【已确认方向】

| 魔法体系 | 定位 | 当前范围 |
|---|---|---|
| 剑指系 | 双指、翻掌、符箓、御符施法 | **MVP 0.2 首先开发** |
| 掌系 | 张掌、掌法、能量波、防御等 | **未来扩展，预留架构与大厅入口** |
| 拳系 | 握拳、蓄力、冲击等 | **未来扩展，预留架构与大厅入口** |
| 其他/双手系 | 多段结印、组合手印、双手协同 | 未来研究，不纳入本次交付 |

架构应以统一的**手型识别 + 动作序列 + 施法状态 + 技能路由 + 特效资源 + 练习课程**为核心，而非将剑指写死为唯一施法系统。

## 3. 剑指系：正式施法动作与规则【已确认需求】

### 3.1 五阶段六步骤

| 步骤 | 玩家操作 | 系统动作 |
|---|---|---|
| ① 剑指起手 | 食指、中指并拢伸直，其余指收拢；**手背朝摄像头** | 确认 `SwordFinger + BackFacingCamera` |
| ② 翻掌召符 | 保持剑指，手背朝向翻到**手心朝摄像头** | 有序识别 `Back → Side → Palm`；单帧手心剑指不可直接召符 |
| ③ 基础符生成 | 翻掌完成 | 在**剑指指尖前方**生成中性基础纸符，开始跟手 |
| ④ 四方向选符 | 保持剑指，上下左右移动整只手 | 以召符位置为锚点识别方向，为原符赋元素 |
| ⑤ 符文待命 | 选符成功 | 元素锁定；仍跟手，等待释放 |
| ⑥ 推掌释放 | 剑指切为 OpenPalm，掌心向前做 Push | 符文过渡到掌前，释放对应魔法并攻击训练目标 |

**必须注意**：切换为张掌本身**不是**释放，必须识别到原有 `OpenPalm + Forward + Push` 的真实推进事件。

### 3.2 四方向映射【已确认需求】

| 方向 | 符文 | 释放法术初版 |
|---|---|---|
| ↑ 上 | 雷符 | 雷击/电流束，高爆发与短暂硬直视觉 |
| ↓ 下 | 火符 | 火球，小范围爆燃视觉 |
| ← 左 | 水符 | 水刃/水流箭，流体冲击视觉 |
| → 右 | 风符 | 风刃/空气冲击，高速切割和轻击退视觉 |

符文类型在成功选定后**一次性锁定**；待命期间移动手指不会重新选符。

### 3.3 指尖绑定【已确认需求】

- **基础符与元素符**都出现在剑指指尖的视觉前方，有实体黄纸质感，不能固定在屏幕中心。
- 横向/纵向移动时随施法手同步移动；手轻微晃动时应用平滑处理，不能漂移或强烈抖动。
- 基础符生成时记录选符锚点；符文的视觉跟随与识别方向的锚点坐标要分开管理。
- 玩家改为张掌后，符文以短暂过渡转移至掌前，再随有效 Push 发射。过渡时不能因为失去剑指而立即误取消。

### 3.4 识别参数草案【设计建议，必须真机标定】

| 参数 | 建议初值 | 说明 |
|---|---|---|
| 起手稳定 | 0.25–0.4s | 新剑指检测器独立参数 |
| 翻掌时间窗口 | 约 0.2–1.2s | 仅允许先背后心、有序连续翻掌 |
| 翻掌末端稳定 | 约 0.15–0.25s | 必须是真正末端姿态 |
| 方向选择期限 | 1.2s | 基础符生成后开始计时 |
| 方向位移门槛 | 相对画面短边约 15% | 试验范围 12–18%；须注意宽高比、镜像和归一化坐标 |
| 主轴优势比 | 1.25 | 上下方向应明显大于左右，反之亦然 |
| 方向确认 | 连续约 3–5 帧 / 0.08–0.15s | 应按真实帧率使用时间判定以避免不同设备偏差 |
| 待命超时 | 4s | 建议数值，非用户最终独立验收结论 |
| 释放冷却 | 约 0.4–0.8s | 尽量复用现有 Push 冷却契约 |

**建议实现细节**：统一使用旋转/镜像处理后的画面坐标；向上/向下须与玩家感知的屏幕方向一致；方向识别采用掌部稳定点或双指参考点的屏幕位移，避免单独指尖抖动造成误选。边界值最终由练习室的数据验证确定。

### 3.5 状态机【设计建议】

```text
Idle
  └─ SwordReady (剑指 + 手背)
      └─ Flipping (有序翻掌)
          └─ BaseRuneReady (中性符生成 + 跟手，记录选符锚点)
              └─ RuneReady (四方向选择并锁定元素，待命且跟手)
                  └─ Casting (张掌 + 有效 Push)
                      └─ Cooldown → Idle

SwordReady / Flipping / BaseRuneReady / RuneReady
  └─ Cancelled (失败/超时/严重追踪丢失) → Idle
```

对于 `RuneReady` 内的剑指→张掌切换，需要**允许释放准备过渡**，不能照搬“方向选择阶段丢剑指立即取消”。同一时间 MVP 只保留**一枚**待命符文；不做多符叠加。

### 3.6 与原技能共存【已确认需求】

- 无待命符文时，正常 Push 仍可释放 `SK001 震山掌`。
- 有待命元素符文时，Push 释放雷/火/水/风对应技能，而不是再同时释放震山掌。
- 需要明确消费事件/冷却归属，防止单次 Push 触发两路技能。

## 4. 符纸与四元素魔法的美术规范【已确认视觉方向，具体资源待制作】

参考用户提供的真人古风施符画面，强调**实体黄符纸 + 朱砂符文 + 自然火焰/能量**，而非西式复杂魔法阵。镜头为**第一人称玩家虚拟施法手**。

| 符类 | 基础外观 | 待命粒子 | 释放/命中 |
|---|---|---|---|
| 基础符 | 竖向米黄/黄纸，金白色朱砂灵纹，淡金光 | 金色微粒、细小悬浮 | 方向选定时原符原位转化 |
| 雷符 | 黄纸+蓝紫/电白能量纹 | 断续电弧、电屑、短电丝拖尾 | 雷束/电击，敌人局部电流和闪白 |
| 火符 | 黄纸+赤红/橙金光纹 | 火苗、火星、热浪 | 收束成火球，爆燃及火花 |
| 水符 | 黄纸+青蓝流光纹 | 水珠、波纹、流体尾迹 | 水刃/水箭，水花与冲击涟漪 |
| 风符 | 黄纸+翠绿/青绿纹 | 旋绕气流、风痕 | 风刃/空气冲击，切割风痕和扬尘 |

共通表现：符纸保留传统长方形纸质本体；有轻微摆动/悬浮/呼吸发光；随指尖同步移动并留下短拖尾；释放前向掌前聚拢；失败/超时则光效减弱并粒子消散。技能伤害、硬直、减速等平衡数值**尚未定稿**，MVP 可先做区别清晰的单次攻击效果。

**需要的资源**：五种纸符、符文图标、召符/转化/跟随/待命/取消特效、四种弹道、四种命中反馈、第一人称虚拟施法手模型及骨架、训练石靶和横屏 HUD 素材。

## 5. MVP 0.2：魔法练习室需求【已确认产品方向】

### 5.1 三个核心页面

1. **练习室大厅**：选择魔法体系；剑指系开放，掌系/拳系为待开放；入口可包含训练记录、设置、帮助。
2. **分步骤教学**：画面中央保持第一人称虚拟手和场景；边缘显示当前步骤、标准手型、实时识别状态/错误原因、下一步引导。
3. **自由练习**：完整施法和攻击训练石魔；边缘显示必要的施法阶段、当前符文、重置/返回；技术数据可隐藏或展开。

### 5.2 六个教学单元【已确认方向】

| 单元 | 教学内容 | 验证目标 |
|---|---|---|
| 01 剑指起手 | 两指标准姿态，手背朝镜头 | 手型/朝向 |
| 02 翻掌召符 | 手背→手心，生成基础符 | 有序序列与触发 |
| 03 四方向选符 | 上雷/下火/左水/右风 | 方向准确性 |
| 04 指尖御符 | 手指移动时符文持续跟随 | 3D/2D 坐标跟随与平滑 |
| 05 推掌释放 | 切张掌、向前 Push、攻击 | 动作切换与技能路由 |
| 06 完整施法 | 从起手到命中一气呵成 | 端到端成功率与耗时 |

每个单元必须能**独立练习**：比如单测四方向时允许提供现成基础符而不用每次重新结印；只有完整施法单元才强制走全流程。

### 5.3 两种运行模式

- **教学模式**：指导提示、参考手势图、通过/失败信息、逐关学习。
- **自由练习/验证模式**：不强制教学步骤，自由施法攻击可重置的训练石靶；可选开发/诊断数据面板。

### 5.4 训练数据【必须实现的验证能力】

建议采集：session ID、设备/版本、目标动作、玩家尝试标记、正确与错误识别结果、漏识别、误触发、重复触发、动作耗时、手追踪丢失、结果年龄、Tracking FPS、Rendering FPS、内存与长时运行变化。数据应支持 CSV/JSON 导出。

**重要**：不能只统计成功识别的动作；需要覆盖系统没识别到的预期动作、负例中无意触发、方向错选，以及从用户发起尝试到最终命中的完整耗时。建议为课程任务显式记录尝试次数。

### 5.5 阶段候选验收指标【设计建议，非已达成】

- 四方向选择正确率目标 ≥95%；完整施法成功率目标 ≥90%。
- 非预期施法误触发：候选目标为每 100 个负例 ≤1 次（具体需定义负例集合）。
- 正确识别输入条件下技能路由不得串技能或重复施法。
- 至少 15 分钟不崩溃、无明显识别性能衰退；记录帧率、延迟、温升/内存。
- 原 `SK001` 震山掌的既有测试与真机回归不得下降。

这些是验收建议而不是现有工程测得数据。

## 6. 横屏、投屏与 HUD 【已确认需求】

- **横屏优先**，16:9 设计基准 `1920×1080`；支持手机 Android 横屏和未来电视投屏。
- 大屏观看要保障文字远距离可读、控件少、高对比、安全边距；真正游戏画面优先。
- 画面中心留给训练石魔、魔法效果与第一人称施法手；HUD 主要沿上下和两侧布局。
- **教学界面**可显示详细手型与识别信息；**自由练习**默认简洁，只显示当前阶段、符咒、必要战斗反馈，数据面板折叠。
- 需要清晰区分“手机摄像头采集画面坐标”和“投屏显示画面坐标”；镜像/旋转处理保证玩家感知的左右/上下方向一致。
- 电视是显示端；当前主要可靠摄像头追踪距离仍只有报告中的约 0.5–0.8m，手机/摄像头摆位和远距体验未来要单独验证。

### 6.1 当前 UI 概念稿状态

**已有多轮概念稿，但并未正式 UI 验收、切图或 Unity 页面实现。** 当前接受的方向是中式玄幻石殿、暗色背景、纸符能量、16:9、第一人称、教学信息与自由练习信息分离。

此前概念图部分出现过**第三人称人物**、**双手同时显示**等与最终要求不一致的内容；**以文字已确认规则为准**，不要照图直接实现错误行为。

## 7. 虚拟施法手与 MediaPipe 骨架映射【已确认原则，待开发】

### 7.1 手部显示规则

1. 底层可以持续追踪左右两只真实手。
2. **默认只渲染当前施法的一只虚拟手**，不因另一手进入画面就自动显示两只。
3. 起手成功后锁定 `activeHand`，直到施法完成/取消或达到明确切换条件，避免左右手跳变。
4. 当前施法手的剑指、张掌、翻腕、左右上下位移必须驱动虚拟手及符纸。
5. 两手同时渲染只作为未来双手组合魔法的扩展能力，MVP 0.2 不要求。

### 7.2 推荐技术设计【设计建议】

- 将 MediaPipe 的手关键点/handedness 适配为统一的 `TrackedHandFrame`，提供手 ID、置信度、坐标、时间戳、朝向和关键点。
- 独立 `ActiveHandSelector` 处理施法手锁定、切换和追踪暂失。
- `VirtualHandRigDriver` 将 21 个关键点/派生指关节旋转映射到虚拟手骨架；虚拟手包括手掌到前臂第一段、魔法师护腕与发光纹路，保持第一人称看到的手背/手心正确。
- `RuneFollowController` 从双指指尖的稳定参考点计算符纸生成与跟随位置，提供平滑、最大跟随延迟和遮挡处理；姿态识别坐标与显示坐标必须分离。
- 当手型从剑指切换为张掌时，保存符咒实体并过渡到掌前，再消费 Push 发射事件。
- 进行横屏旋转、前置摄像头镜像、左右手、180° 翻转及电视投屏全链路回归。

**尚需实测确定**：虚拟手 3D 深度、指尖偏移距离、骨架关节可驱动程度、模型/骨架约束、跟随滤波参数、手部遮挡策略、左右手镜像规则。

## 8. 开发拆解与实施顺序【建议】

### P0 — 底层稳定与可观察性

### P1 — 符咒逻辑闭环

- `RuneCastStateMachine`、`DirectionSelectionRecognizer`、`RuneFollowController`。
- 实现上雷/下火/左水/右风单次锁定，符咒超时与取消，Push 路由与 SK001 兼容。

**不包含**：正式剧情关卡、怪物 AI 系统、技能树、多人联机、双手组合技、多符组合等。

## 10. 开发时必须遵守的产品契约

1. 不重做 v0.1.0 基础识别；保护震山掌基线。
2. 练习室优先于正式游戏开发，核心目的是教学和技术可行性验证。
3. 剑指起手是**手背朝屏幕**，翻转终点是**手心朝屏幕**，必须检查动作顺序。
4. 基础符/元素符在**指尖前方**，**始终跟随施法手**直到准备推掌释放。
5. 元素选择固定为：上雷、下火、左水、右风；选中即锁定。
6. Push 是释放门槛；仅张掌不释放；有符不应同时发震山掌。
7. 横屏 16:9、电视远距离可读、第一人称，默认只显示当前施法的一只手。
8. 底层可追踪两手，但施法中需保持活动手身份稳定。
9. 掌系、拳系预留扩展，但当前不做完整体系。
10. 设计参数是**起始建议**，不能未经测试当作稳定识别基线。
11. 区分识别率、动作尝试次数、误触率、端到端施法成功率和性能指标。
12. 美术参考图里如出现双手、非第一人称、UI 太拥挤等，以本文件的已确认需求为准。

## 11. 尚待确认的事项（不是既定需求）

- 虚拟魔法手角色模型、左右手外观及骨架标准、指尖三维空间偏移与遮挡策略。
- 召符/翻掌时间、方向门槛、手型容错、待命超时与允许短暂失跟的最终量化值。
- 活动手选择的 UI/动作触发方式（首个稳定手、设置指定左右手、手动切换等）。

- 课程通过规则、是否需要解锁机制、用户成绩如何存储同步。

以上不阻碍先实施可配置和可验证的 MVP；但不应静默视为用户已经最终确认。
